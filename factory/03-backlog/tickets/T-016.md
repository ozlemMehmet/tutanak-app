## Kapsam
T-003'un PR'inda (#3) SonarCloud Quality Gate iki kosulda dustu — **yalnizca yeni kod**
uzerinde:

- `D Reliability Rating on New Code` (gereken ≥ A)
- `C Security Rating on New Code` (gereken ≥ A)

T-003 yine de merge edildi: SonarCloud branch protection'da **zorunlu check degil**, zorunlu
olan `lint + typecheck + migrate + test + build` yesildi. Yani bu ticket bir kapiyi acmak
icin degil, birikmeden temizlemek icin var.

**Onemli kisit:** proje SonarCloud'da ozeldir ve analiz CI adimi degil, SonarCloud GitHub
App'inin otomatik analizidir (`ci.yml`'de sonar adimi yoktur). Bulgu listesi kimliksiz
API'den okunamadi. Bu ticket'in **ilk isi** gercek bulgu listesini almaktir; asagidaki iki
madde token'siz yapilan kod incelemesinden cikan **adaylardir**, dogrulanmis Sonar ciktisi
degildir. Once liste alinmali, sonra ona gore duzeltilmelidir.

## Kabul Kriterleri (test edilebilir)
- [ ] PR'da SonarCloud Quality Gate **passed** doner (yeni kod icin Reliability ve Security
      derecesi ≥ A).
- [ ] Gercek bulgu listesi alinip devlog'a yazilir (hangi kural, hangi dosya/satir, ne
      yapildi) — tahminle degil, kaynagindan.
- [ ] `apps/api/src/modules/auth/auth.service.ts` icindeki `expiresIn` hesabi,
      imzalanan token'i geri **decode ederek** degil, yapilandirmadaki `JWT_EXPIRES_IN`
      degerinden uretilir; `jwtService.decode()` sonucunun `null` olabilecegi kod yolu
      kalmaz. Mevcut auth birim/e2e testleri degistirilmeden gecer.
- [ ] Test kaynaklarindaki sabit kimlik bilgileri (`TEST_JWT_SECRET`, spec dosyalarindaki
      sabit parolalar) Sonar tarafindan zafiyet olarak sayilmaz — ya analiz kapsamindan
      dislanarak (`sonar.test.inclusions`/`sonar.exclusions` veya proje ayari) ya da baska
      bir yolla. Secilen yontem devlog'da gerekcelendirilir.
- [ ] `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:e2e` temiz.

## Kapsam DISI
- SonarCloud'u CI'a zorunlu check olarak eklemek — bu bir kapi politikasi karari, ayrica
  karara baglanmali (bkz. Teknik Notlar).
- Test dosyalarindaki sabit parolalari gercek sirlarla degistirmek — testler sir
  kullanmamalidir, sorun kapsam ayarindadir.
- Auth davranisinin degismesi: token omru, cost, hata kodlari aynen kalir.

## Teknik Notlar (varsa)
- Aday bulgular (dogrulanmamis):
  - *Reliability:* `auth.service.ts:47` — `this.jwtService.decode<AccessTokenClaims>(token)`
    `null` donebilir, hemen ardindan `claims.exp - claims.iat` okunur. Token bir satir once
    imzalandigi icin calisma zamaninda tetiklenmez, ama statik analiz olasi null
    dereference olarak isaretler. Zaten dolambacli: `JWT_EXPIRES_IN` yapilandirmada mevcut.
  - *Security:* `test/auth.e2e-spec.ts:16` ve `test/health.e2e-spec.ts:15` sabit
    `JWT_SECRET`; `auth.controller.spec.ts` / `auth.service.spec.ts` sabit parolalar.
    Sonar'in "hard-coded credentials/secrets" kurallari bunlari Vulnerability sayar ve
    Security Rating'i dusurur. Gercek bir acik degil, kapsam ayari sorunudur.
- Gate zorunlu olmadigi surece bu tur bulgular sessizce birikir. Sonar'i zorunlu check
  yapmak isteniyorsa once bu ticket'la yesile cekilmeli, sonra branch protection'a
  eklenmelidir — sirasi ters olursa tum merge'ler kilitlenir (T-002'de yasanan durum).
